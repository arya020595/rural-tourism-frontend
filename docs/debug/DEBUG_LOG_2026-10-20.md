## 1. Cancelling a booking jumped back to the booking list

**Symptom:** after cancelling from the booking detail page, the app went to
the booking list (or the dashboard).

**Root cause:** `booking-detail.page.ts` `cancelBooking()` called
`this.goBack()` after success — the same pattern already removed from Recall.

**Fix:** stay on the page; it already switches to the "Cancelled" status and
the cancelled-state buttons. Tested in the browser (stays on
`/booking-home/detail/:id`, status Cancelled, cancelled on the server).

## 2. Cancelling from the booking list showed nothing

**Symptom:** the ⊘ cancel icon in Table View refreshed the list with no
message; a failure was only logged to the console.

**Fix:** `booking-home.page.ts` shows "Booking cancelled successfully" (or the
server's error) via `ToastService`, like the detail page. Tested: message
shown, booking cancelled on the server, page stays on the list.

## 3. Booking calendar: pick month/year from a pop-up

**Request:** the calendar could only move one month at a time with ‹ ›.

**Change:**
- The title is two buttons — month name and year — styled as light boxes
  (a ▾ arrow was tried and removed: it's a pop-up, not a dropdown). Clicking
  the month opens the month grid; clicking the year opens the year list
  (2020 → current year + 5), then the month grid. Same picker as the
  dashboard Trend filter (`booking-date-sheet`, `pickMode="month"`).
- `booking-date-sheet.component.ts`: new `startInYearView` input (month mode
  opens on the year list).
- `booking-home.module.ts` imports the standalone `BookingDateSheetComponent`.
- Phones (< 576 px): smaller title, gaps and arrows so "September 2026" and
  the ‹ › arrows stay on one line at 360 px.

**Testing:** month → Mar; year → 2025 → Dec; arrows still work; screenshots at
1280 px and 360 px.

**Gotcha:** Angular removes whitespace between elements, so the title's text
is "October2026" (no space) — tests must not compare the text with a space.

## 4. Evening bookings shown on the next day in the calendar

**Symptom (production):** 4 Jan 2026, 6:54 PM showed on 5 Jan in the booking
calendar; morning bookings were fine; the detail page was correct.

**Root cause:** `activity_date` is the Malaysia date/time **as typed**, stored
in the UTC fields (e.g. `"2026-01-04T18:54:00.000Z"`). The detail/edit pages
read it literally (by design), but some readers used `new Date(...)`, which
converts to Malaysia time and adds 8 hours:

| Reader | Was |
|---|---|
| booking calendar (`booking-home` `resolveBookedDate`) | +8 h → next day after 4 PM |
| booking list time (`booking-home` `formatTime`) | +8 h |
| My Transaction time (`extractTime`) | +8 h |
| offline calendar dots (`offline-queue` `getCachedBookedDates`) | +8 h |

Backend side (saving, the booked-dates endpoint, PDF): see the backend log §2.

**Fix:** new `utils/activity-date.util.ts` — `activityDateKey()`
(`YYYY-MM-DD` from the string) and `activityTime()` (`HH:mm` from the string,
midnight = no time), used by the four readers above. The unused
`booking-home` `formatTime` and My Transaction `extractTime` were removed.

**Rule for new code:** for `activity_date`, never `new Date(value)` and read
local date/hours — use `activityDateKey()` / `activityTime()`.
`created_at` / `receipt_created_at` are real instants; those still convert.

**Testing:** "4 Jan 2026 6:54 PM" booking through the dev backend — January
2026 calendar marks only the 4th, the 4 Jan panel lists it, list shows
04-01-2026, detail shows 04/01/2026 06:54 PM.
