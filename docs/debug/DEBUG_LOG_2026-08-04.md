# Frontend Debug Log — 2026-08-04

Debugging session log for the Rural Tourism (RUTeC) Ionic + Angular frontend.
Documents the bugs diagnosed on this date, their root causes, and how to confirm
them. Future debugging sessions should be recorded in a new `DEBUG_LOG_<date>.md`
file rather than editing this one.

> Stack: Ionic 8 + Angular 18 + Capacitor 7. Offline-first (IndexedDB + service
> worker). API base URL per environment in `src/environments/`.

---

## 0. First moves for any bug

1. **Open DevTools → Console.** Most "it doesn't work" bugs print an error there.
   Do not skip this — several bugs below look like backend/data issues but are
   actually client-side exceptions.
2. **Open DevTools → Network.** Find the relevant `/api/...` request. Note the
   **status code** and **response body**. This alone distinguishes:
   - `200` + empty/expected data → the API is fine; bug is in the frontend.
   - `403` → permission / association-scope issue (see §3).
   - `401` → auth/token issue (re-login, or token missing a field).
   - `500` → backend; switch to the backend debugging guide.
3. **Application → IndexedDB / Local Storage** — inspect cached data for
   offline/stale-data bugs (see §1, §2).

## 1. Empty dropdown / list even though the API returns data

**Real case:** the package-booking "Company/Package" dropdown was empty in
production; no company could be selected. The DB had the data, the API returned
it, but the dropdown stayed empty.

**Root cause:** `localStorage.setItem(...)` threw **`QuotaExceededError`** (the
~5 MB localStorage quota was full), and it was called *before* the data was
applied to the UI:

```ts
// BAD — setItem throws, so applyX(data) never runs → empty UI
next: (response) => {
  localStorage.setItem(cacheKey, JSON.stringify(data)); // throws when full
  applyCompanies(data);                                  // never reached
}
```

**How to spot it:** Console shows
`QuotaExceededError: Failed to execute 'setItem' on 'Storage'`.

**The rules (already applied in the booking forms):**
- **Apply data to the UI first, cache second.** Caching is best-effort and must
  never block rendering.
- **Never write large/aggregated data to `localStorage`.** Per-company product
  lists overflow the quota. Use **IndexedDB** (`OfflineQueueService`
  `cacheProducts` / `cachePackageCompanies`) instead. localStorage is only for
  small values (token, user, uid).
- Wrap any remaining `localStorage.setItem` / `JSON.parse` in try/catch.

**Related:** `docs/OFFLINE_BOOKING_IMPLEMENTATION.md` for the offline data model.

## 2. Offline data missing / stale

Offline product & company data lives in **IndexedDB** (`rural_tourism_offline`),
written by `SyncService.prewarmCaches()`. Bookings, products, and the package
company list are all cached there.

**When caching happens (`prewarmCaches`):**
- On login (login page calls it after successful auth).
- On app startup if already logged in and online.
- When the app returns to foreground while online.
- After the offline queue drains.

**Operators only.** Prewarm skips tourist/association users on purpose — they
lack permission for the product/company endpoints and would get 403s.

**Gotcha:** prewarm loops over *all* package companies sequentially (many API
calls, several seconds). If the user goes offline *before* it finishes, later
companies won't be cached. Real-world flow (login → use online a bit → lose
connection) caches everything.

**How to verify offline caching works:**
1. Log in as an operator, online.
2. DevTools → **Application → IndexedDB → `rural_tourism_offline`**. After a few
   seconds you should see `product_cache` and `company_cache` populate.
3. DevTools → **Network → Offline** (or Application → Service Workers → Offline).
4. Open the package booking form → the Company dropdown should still list
   companies (served from IndexedDB).

**Stale localStorage cleanup:** obsolete `products_cache_*` and
`package_companies_cache` keys are deleted once per load in `src/main.ts`. If you
see them in Application → Local Storage on an updated build, hard-reload.

## 3. "You do not have permission to perform this action" (403)

Two distinct causes — check the Network tab to tell them apart.

**A. The role genuinely lacks the permission.**
- Endpoint fails with 403; response mentions the missing permission.
- Menu items and routes are permission-driven (`menu.service.ts`,
  `app-routing.module.ts` guards). If a menu item is hidden or a route
  redirects to `/unauthorized`, the role is missing that permission.
- **Booking a product needs `product:read`** (the booking form loads products
  via `/api/products/company/:id`). Granting only the `booking:*` permissions is
  not enough — `product:read` is separate (Master Data / Product Management).

**B. Stale token after a permission change.**
- Permissions are baked into the **JWT at login**. Changing a role's permissions
  in Role Management does **not** update an already-logged-in session.
- **Fix:** log out and back in so the new token carries the updated permissions.
- This is the #1 reason a permission change "doesn't take effect."

**Menu/route consistency:** a menu item's `permission` should match its route
guard's `permissions`. A mismatch means the item hides but the route stays
reachable by URL (or vice-versa). Keep them aligned.

## 4. Sidebar / menu shows the wrong items

- The sidebar is built from `MenuService.getVisibleMenuItemsForCurrentUser()`,
  filtered by the logged-in user's `roles_permissions` (from the token) plus an
  optional per-item `roles` restriction.
- **superadmin holds only `*:*`** (no granular codes). Its menu is handled
  specially: all items except those in `SUPERADMIN_HIDDEN_MENU_IDS`, still
  respecting each item's `roles`.
- If a permission change doesn't hide a menu item, check: (a) re-login (stale
  token, §3B), and (b) whether the item is gated with **OR** logic
  (`permission: ['a', 'b']`) — the item shows if the user has *either*.

## 5. Wrong date / month on receipts and PDFs

- On-screen receipt pages (`receipt`, `receipt-activity`, `receipt-package`)
  format dates in the component (`formatMyDate`). **The QR-linked PDF is
  generated by the backend** (`utils/receipt*PdfGenerator.js`) with its *own*
  formatter. Changing the page does **not** change the PDF, and vice-versa.
- If the page and PDF show **different date values**, they're reading different
  fields. The receipt-issued date resolves as
  `receipt_created_at → updated_at → created_at` — keep both sides consistent.
- Full Malay month names (Januari, Julai, Ogos…) live in the month arrays; both
  frontend pages and backend generators have their own copy.

## 6. A field "shows as saved" but is missing on the receipt/PDF

**Real case:** the package booking's date was entered in the form and the detail
page displayed it (`04/08/2026`), yet the deposit PDF showed `-`.

**Root cause:** the value was **dropped from the submit payload**. Each booking
type has its own payload builder in `booking-add.page.ts`
(`buildActivityPayload` / `buildAccommodationPayload` / `buildPackagePayload`).
`buildPackagePayload` was missing `activity_date`, so the date never reached the
API → stored as null → PDF empty.

**Why it looked saved:** the detail page re-renders from the frontend booking
model's in-memory state (`bookingDate`), not from what was persisted. So the UI
showed the value even though the DB row had none.

**How to spot it:** the field shows on the form/detail page but is `-`/null on a
freshly generated PDF *and* in the DB. Check the **Network tab request body** on
submit — if the field isn't in the payload, the builder dropped it. Compare the
type-specific payload builders; they drift (activity had it, package didn't).

**Note:** the backend `create` payload already accepted the field for all types
(`bookingsService.js` includes `activityDate` for every booking type). The bug
was entirely on the frontend submit side.

## 7. Package PDF shows empty product/activity fields

The booking deposit PDF (`utils/bookingPdfGenerator.js`) originally had only two
branches: accommodation vs. activity. A **package** booking fell into the
activity branch → showed an empty `AKTIVITI/ACTIVITY` (packages have no single
`productName`, they have multiple items). Also `getBookingPdfData` did not fetch
the package items. Fix: fetch `packageItems` in the service and add a package
branch to the generator (label `PAKEJ/PACKAGE` + numbered item list). When a PDF
shows blanks for a whole booking type, check for a missing type branch first.

## 8. Native (APK) issues that don't reproduce in the browser

- **Modal/overlay hidden behind the top nav:** a custom overlay placed *inside*
  `<ion-content>` is trapped below `<ion-header>` in the stacking order on
  native. Move the overlay to be a sibling of `<ion-content>` and give it a high
  `z-index`. Respect `env(safe-area-inset-*)` so it clears the status bar.
- **API calls fail only in the APK:** the app uses `environment.native.ts`
  (swapped in by the `native` build config). Two things bite:
  - The production URL is `http://` (cleartext). Android blocks cleartext by
    default — the host must be whitelisted in the Android network-security
    config.
  - `NODE_ENV=production` must be set on the server so the CORS allowlist
    (which includes `capacitor://localhost` / `http://localhost`) is active.
- **PDF-in-iframe blank on device:** if the uploads server sends
  `X-Frame-Options`/CSP that blocks framing, the preview iframe renders blank.
  Rebuild the APK after any `environment.native.ts` change.

## 9. Verifying a change locally

- **Typecheck:** `npx tsc --noEmit -p tsconfig.json` catches most breakage
  without a full build.
- **Run the app:** `ionic serve` (dev server at `http://localhost:8100`),
  backend at `http://localhost:3000`.
- **Drive the browser** with Playwright (already a dev dependency) for
  end-to-end checks. Ionic `<ion-input>` renders a real `<input>` in shadow DOM —
  target `ion-input[name="x"] input` to fill it.
- **Inspect IndexedDB from a script:** open `rural_tourism_offline` and read the
  object stores (`product_cache`, `company_cache`, `booking_cache`) to confirm
  caching.
