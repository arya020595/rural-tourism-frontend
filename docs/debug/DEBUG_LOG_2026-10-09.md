## 2. Refresh button and pull-to-refresh

**Request:** the installed app has no browser refresh, so after going offline
and back online there was no way to force a fresh state.

**Added:**
- `services/app-refresh.service.ts` — online: sync queued offline bookings,
  then `window.location.reload()`; offline: show a message and do nothing
  (reloading with no connection could leave a blank screen).
- `_shared/refresh-button/refresh-button.component.ts` — header button beside
  the bell on all 13 operator pages. Form pages (Booking Add/Edit, E-Receipt
  Add, Company Profile) use `[confirmReload]="true"` so unsaved input isn't lost.
- `_shared/refresh-button/pull-refresh.directive.ts` — `<ion-refresher
  slot="fixed" appPullRefresh>` on the 9 list/view pages only (not on forms,
  where a stray pull would wipe input).

**Gotcha:** `ion-refresher` must be a direct child of `ion-content` with
`slot="fixed"` — that's why it's a directive on the refresher, not a wrapper
component.

## 3. App kept showing the old version after a Play Store update

**Symptom (found by analysis, then reproduced):** after an update, the app
could keep loading the previous version's screens; the website likewise after
a deploy.

**Root cause:** `src/sw.js` served **everything** cache-first — including
`index.html` — from a cache named `app-shell-v1` that never changed. Cache
Storage survives Play Store updates, and the saved `index.html` points at the
old JS bundles, which were cached too. Capacitor 7 runs service workers inside
the Android app by default (`resolveServiceWorkerRequests = true` in
`@capacitor/android`), so this affected the app as well as the website.

**How it was confirmed:** headless Chrome + the real `sw.js`: after "releasing"
a new version, every reload and a new tab still showed the old one.

**Fix:**
- `main.ts`: no service worker in the Android app (its files are inside the
  APK and load offline anyway); on start-up it unregisters the old one and
  deletes `app-shell-*` caches. `prewarm-assets-v1` is kept (e-receipt reads
  images from it). IndexedDB (offline bookings) is not touched.
- `sw.js` (website): page navigations are **network-first** (saved copy only
  when offline, stored under `/index.html` so any route works offline); hashed
  JS/CSS stay cache-first; cache renamed `app-shell-v2` so `activate` deletes
  the stale v1.

**Gotcha:** devices that already had the old cache show the old version **one
more time** after updating; the new `sw.js` then clears it.

## 4. No booking dots on the calendar when offline

**Root cause:** `booking-date-sheet` only got dots from `GET
/api/bookings/booked-dates`.

**Fix:** when offline (or the request fails) the dots come from bookings saved
on the device, including ones made offline —
`offlineQueue.getCachedBookedDates()`, same rules as the backend
(activity/package on the activity date, accommodation check-in → check-out
inclusive, cancelled/rejected skipped).

## 5. Booking made offline appeared twice when offline again

**Symptom:** offline booking synced fine, but offline again the list showed it
twice — one row with a UUID (e.g. `0d945e5e-…`) and the real one (#2772).

**Root cause:** booking-add / ereceipt-add cache a placeholder under the
idempotency key so it shows offline. After sync the server copy was cached too,
but the placeholder was never removed.

**Fix:** `syncCreate` removes the placeholder and caches the server copy;
`getCachedBookings()` also prunes placeholders whose queue item is synced or
gone (cleans phones that already have one).

## 7. Tapping a notification opens the booking

Reminder notifications already store the booking ID in `related_id` (backend
`bookingReminderService`). The `Notification` interface used `booking_id`,
which the API never returns. `notificationService.getBookingId()` reads
`related_id` (falling back to `booking_id`); the desktop panel and the phone
Notifications page open `/booking-home/detail/:id` (only with `booking:read`).

## 8. Opening the app offline logged the user out

**Symptom (found during the login analysis, confirmed in code and by browser
test):** opening the app with no connection sent the user to the login page —
where they can't log in without internet.

**Root cause:** on start-up `AuthService.initializeAuthState()` calls `GET
/auth/me`, and its error handler cleared the session on **any** error,
including "no internet" (status 0).

**Fix:** only a 401 ends the session (the HTTP interceptor handles that and
shows why); network/server errors keep the saved session.

## 9. 30-day login, renewal and logout reasons

Backend side: see the backend log §1.

- **Renewal:** `AuthService.checkSession()` calls `/auth/me` when the app comes
  back to the foreground (`visibilitychange`), when the connection returns
  (`online`), and every 6 hours — at most once per 30 minutes, never offline.
  `refreshSession()` stores `data.token` when the server sends a renewed one.
  A check that can't reach the server (no internet) does **not** count towards
  the 30-minute throttle — so after opening the app offline, the connection
  coming back renews the login straight away. (Found while testing long
  offline periods: before this, the failed start-up check counted, and renewal
  waited up to 30 minutes after reconnecting.)
- **Long offline periods:** the 30 days count from the last time the app
  reached the server. Offline the app keeps working with an expired token (no
  local expiry check); on reconnecting an expired login sends the user to the
  login page with "Sesi tamat / Session expired", and bookings made offline
  stay queued and sync after logging in.
- **Logout messages** (`http-interceptor.service.ts`, from the 401 `code`):
  deactivated, account removed, password changed elsewhere, session expired —
  Malay / English.
- **Change password:** `authService.changePassword()` stores the new token from
  the response; otherwise the current device would be logged out by its own
  password change.
- **Sync no longer uses the phone's clock:** `SyncService.isTokenValid()` only
  checks a token exists; expiry is the server's call (a wrong phone date used
  to stop syncing).
- **Login ended mid-sync:** a 401 while sending a queued booking keeps it
  `pending` (note "Waiting for login", retry not used up) and stops the run;
  it syncs after the next login. Previously any 4xx marked it
  `permanently_failed`.
- Unsynced bookings of a user deactivated while offline sync when a colleague
  from the **same company** logs in on that phone (queue is per company) —
  agreed behaviour.

## 10. Same booking sent twice when the connection came back

**Symptom:** operators saw "duplicate"/failed offline bookings after
reconnecting. In testing: queue item showed *pending, retry 1, "Validation
error"* although the booking existed on the server.

**Root cause:** reconnecting fires both the Capacitor network event and the
browser `online` event; each triggers `SyncService.triggerSync()`. The
`isSyncing` flag was only set **after** `await acquireLock()`, so both calls got
through, both took the (non-atomic) lock, and the booking was POSTed twice. The
server's unique `idempotency_key` index rejected the second copy (so no
customer was double-booked), but that 500 flipped the already-synced item back
to pending → after 3 retries a "failed sync" for a booking that exists. The
same race could happen when the 30-second sync interval coincided with a sync
started by booking-add.

**Fix:** `triggerSync()` sets `isSyncing` before its first `await`. Also, a
successful sync now clears `error_message` (old "Network error" notes used to
remain on synced items).

**Confirmed by test:** exactly 1 `POST /bookings` on reconnect.

**Not covered:** two browser **tabs** can still race (the IndexedDB lock is
read-then-write, not atomic) — website only, and the server still prevents a
double booking.

## 11. Remember me

**Request:** save username **and** password for users who forget passwords.

**Design:**
- **Android app:** username + password in encrypted storage
  (`@aparajita/capacitor-secure-storage` 7.1.6, Android Keystore) —
  `services/remembered-login.service.ts`.
- **Website:** username only (localStorage); the password is left to the
  browser's password manager. The password field had `autocomplete="off"`,
  which blocked it — now `autocomplete="username"` / `"current-password"`.
  The page itself never stores the password (no encrypted storage exists in
  the browser).
- Checkbox "Ingat saya / Remember me" under the password, unticked by default;
  unticking forgets the saved login immediately; logout keeps it; a saved
  password that fails (401) is forgotten and the user is asked to type it.

**Gotchas:**
- `npm install` fails with an `ERESOLVE` on the existing eslint packages — the
  project installs with `--legacy-peer-deps` (README, CI).
- The plugin lists `@capacitor/app` ^7 as a dependency, so npm nests a second
  copy (the project uses 6.0.1). Harmless: the plugin never imports it.
- At 360 px the checkbox label was cut off; fixed with
  `ion-checkbox::part(label) { white-space: normal }` and
  `white-space: nowrap` on "Lupa Kata Laluan?".
- Edge/Chrome only fill the password after the user clicks **Save** on the
  browser's "Save password?" prompt (or via the key icon in the address bar).

## 12. Testing notes

- **Browser tests (Puppeteer, local backend, temporary users deleted after):**
  Remember me (9/9); login ending during a sync, renewal triggers, password
  change from the screen (15/15). Useful tricks: write queue items straight
  into IndexedDB (`rural_tourism_offline` → `offline_booking_queue`), dispatch
  `window` `online` / `document` `visibilitychange` events, and override
  `Date.now` in the page to get past the 30-minute check throttle.
- **Long offline periods (Puppeteer, 14/14):** tokens signed with an `iat`
  25 and 31 days in the past (the server only compares `exp` with now, so this
  is the same as waiting). 25 days: opens offline and stays logged in,
  offline booking syncs on reconnect (sent once), login renewed 5 → 30 days.
  31 days: opens offline and stays logged in, reconnect → login page with
  "Sesi tamat", booking kept pending (no retry used, nothing sent with the
  expired token), after logging in it syncs exactly once and the new login
  lasts 30 days.
  Note: these tests block requests to the API rather than switching the
  network off, so the browser still reports online and the interceptor shows
  "Unable to connect to server" — on a phone that is really offline that
  message is suppressed (`networkService.isOnline` is false).
