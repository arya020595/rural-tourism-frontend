## 1. Booking silently resolves to another company's product (cross-company product-name collision)

**Symptom:** an operator (Justin Ranny, company "Kiulu Eco-Tourism") selected
"Kayak" from his own company's activity dropdown when creating an offline
booking. On sync, it landed in the app's Sync Conflict screen with the
server rejecting it: `Forbidden. You can only process bookings for products
in your own company.` — even though Justin's own company genuinely has its
own "Kayak" product.

**Root cause:** `booking-add/booking-add.page.ts`'s `findProductByName()` —
which re-resolves the operator's typed/selected product **name** back into a
`product_id` at submit time — called `this.productService.getProductsByLocation(...)`
first (a backend endpoint that returns products from **every company sharing
the caller's `Company.location` string**, not just the caller's own company).
The dropdown itself (`loadActivityOptions()`) was correctly scoped to the
operator's own company via `getProductsByCompany()`, but the two functions
used different, inconsistent scopes — so a duplicate product name in the same
location pool could win the name-match and attach the wrong company's
`product_id` to the booking.

**Why this is far more likely for migrated Kiulu/KTA accounts specifically:**
all 37 companies migrated from the old Kiulu system share the literal
`location: 'Kiulu'` value (the old system had no real per-company address
data, so the migration used a single placeholder location for all of them —
see the backend's `docs/LEGACY_DB_MIGRATION_ANALYSIS.md`). This merges all 37
companies into one shared, collision-prone pool for any location-scoped
query. A direct scan of the 37 migrated companies' product names found 47
duplicate names among them alone (e.g. "hiking" in 27 different companies,
"kayak" in 5). A typical pre-existing company has a real, distinct address,
so its location-scoped pool is naturally much smaller and collisions are far
less likely — though not architecturally impossible for non-migrated
companies either.

**Fix:** `findProductByName()` now tries the operator's **own company**
first — `getProductsByCompany(companyId)` (online), falling back to the
same company's cached IndexedDB copy offline — instead of the location-wide
list. This guarantees a booking can only ever resolve to a product the
operator's own company actually owns. `getProductsByLocation()` itself was
left unchanged (it's still legitimately used elsewhere, e.g. package-booking
referral-company lookups, which genuinely need to browse other companies'
products).

**Verify:** as an operator whose company shares a `location` with another
company that has a same-named product, create a new activity/accommodation
booking selecting that name. Confirm the synced booking's `product_id`
belongs to your own company
(`SELECT company_id FROM products WHERE id = :product_id` should match your
own `company_id`), not the other company's.

**Recurrence found in a second, separate entry point (same day, after the fix
above shipped):** the exact same 403 (`Forbidden. You can only process
bookings for products in your own company.`) reproduced again, this time via
the **E-Receipt / walk-in booking form** (`/e-receipt` →
`ereceipt-add.page.ts`, a completely different component from
`booking-add.page.ts`) — an operator ("abu"/Fadzil, company_id 59) booking
"Kayak" ended up with `product_id = 27`, which belongs to a different company
(id 63, "Dapako Hill - Lingga Eco Tourism"). Root cause: `ereceipt-add.page.ts`
has its **own independent copy** of `findProductByName()` (not shared with
`booking-add.page.ts`), and this copy still called
`this.productService.getProductsByLocation(...)` first — the fix above was
never applied here because it's a separate file with duplicated logic, not a
shared helper. Fixed identically: company-scoped `getProductsByCompany(companyId)`
first, falling back to the same company's cached IndexedDB copy offline.

**Full-codebase audit performed after the recurrence** (searching for every
place that resolves a product/activity/homestay *name* back into a
`product_id`, not just the two already known): confirmed `booking-edit.page.ts`,
`booking-forms/components/activity-booking-form.component.ts`,
`accommodation-booking-form.component.ts`, and
`package-booking-form.component.ts` were all **already correctly
company-scoped** (no fix needed). A final grep for `getProductsByLocation`
across the entire frontend after both fixes confirms **zero remaining call
sites** — the method is now only referenced in its own definition
(`services/product.service.ts`), meaning nothing in the app can trigger this
class of bug anymore, including any future duplicate-name collision beyond
Kiulu/KTA companies.

**Lesson:** this bug existed in two near-identical, independently-copied
functions across two files; fixing one did not fix the other, and the
recurrence looked at first glance like the fix hadn't worked at all. When a
fix targets one function found via a symptom, grep the whole codebase for
other copies of the same logic (by the buggy API call it makes, not just the
function name — `findProductByName` could easily have been renamed or
reimplemented slightly differently in a third location) before considering
the class of bug closed.

## 2. PWA install prompt / browser tab still showed old "Rural Tourism" branding and logo

**Symptom:** clicking the browser's "Install app" prompt on `rutec.my` showed
the app name "Rural Tourism" with the old logo, even though every in-app page
(login, dashboard, etc.) already displayed the current RuTEC/Explore Sabah
branding.

**Root cause:** a PWA's install-prompt name/icon comes entirely from
`src/manifest.webmanifest` — not from any page content — and this file had
never been updated as part of the app's earlier rebrand:
- `name`/`short_name`: still `"Rural Tourism"`.
- `icons`: all three entries (`Rural_192.png`, `Rural_144.png`,
  `Rural_512.png`) pointed at the pre-rebrand logo files.

Separately, `src/index.html` had the same gap across several tags (`<title>`,
favicon `<link rel="icon">`, `apple-mobile-web-app-title`,
`mobile-web-app-title`) — plus a genuine pre-existing bug unrelated to
branding: the Apple/mobile touch-icon `<link>` tags referenced
`assets/icon/Rural_logo.png` (underscore), but the actual file on disk is
named `Rural logo.png` (space) — those two `<link>` tags had been silently
404ing regardless of which brand's name was on them.

**Fix:**
- Found a correctly-cropped, square RuTEC icon already used for the Android
  native launcher
  (`android/app/src/main/res/mipmap-xxxhdpi/ic_launcher_foreground.png`,
  432×432, transparent-safe on white). Copied it to
  `src/assets/icon/rutec_pwa_icon.png` and pointed the manifest's `icons`
  array at it for all declared sizes (declared the true native size, 432×432,
  as the largest entry rather than falsely claiming a 512×512 file that
  doesn't exist — browsers pick the closest match and downscale cleanly).
- Updated `manifest.webmanifest`'s `name`/`short_name` to `"RuTEC"`.
- Updated `index.html`'s `<title>`, favicon, apple-touch-icon,
  mobile-touch-icon, and their title `content` attributes to match, fixing
  the underscore/space filename bug in the same pass.
- Also swapped the receipt-PDF fallback logo (shown when a company has no
  logo of its own) from the old `RuralT Logo.png` to the new
  `rutec_pwa_icon.png` in 3 receipt pages
  (`receipt.page.ts`, `receipt-activity.page.ts`, `receipt-package.page.ts`)
  and the offline asset-prewarm list (`services/sync.service.ts`), per
  explicit user confirmation this was in scope.

**Not done (no image-processing tooling available in this session):**
properly-sized, individually-optimized 144×144/192×192/512×512 PNGs — a
single 432×432 source is reused for all three manifest entries instead. Good
enough visually for an install-prompt icon; revisit if a design tool
generates dedicated exports later.

## 3. Play Console release build & versioning (walkthrough, not a bug)

Not a defect — recorded here since it's part of this session's work and the
next release will hit the same steps.

- Confirmed Play Console production access was already granted; open testing
  is optional, not a gate — went straight to Production → Create a new
  release.
- Generated the signed AAB via Android Studio (`Build → Generate Signed App
  Bundle or APK → release`), reusing the existing keystore from the prior
  closed-testing release (`android/key.properties` — **contains plaintext
  keystore/key passwords committed inside the `android/` folder**; flagged to
  the user as worth double-checking is excluded from source control, not
  otherwise touched this session).
- First upload attempt failed: `Version code 3 has already been used. Try
  another version code.` — bumped `android/app/build.gradle`'s
  `versionCode` 3 → 4 and `versionName` "1.0.2" → "1.0.3", rebuilt.
- The "no deobfuscation file" warning on upload is advisory only (relevant
  only when `minifyEnabled true`/R8-ProGuard is active) — safe to ignore and
  proceed for a Capacitor app whose logic runs in the WebView.

## Features built this session (frontend side)

**Master Data (products) soft-deactivation UI:**
- `master-data.page.html`/`.ts`/`.scss` — added a Status column (toggle +
  Aktif/Tidak Aktif label) to the products table, wired to
  `productService.updateProduct(id, { is_active })` with optimistic UI update
  and revert-on-error. Renamed the Type column header to "Jenis Produk" and
  its cell values to Malay-only ("Aktiviti"/"Tempat Penginapan") per user
  request; reordered columns to Type → Product Name (later relabeled "Nama
  Produk") → Created At → Updated At → Status.
- Went through **two full rebuild cycles** on this table's action-button
  markup: the first pass reused the existing `<ion-button>`-based action
  icons (info/edit/delete) inside the new layout, which produced a
  persistent, hard-to-pin-down broken/discontinuous row-divider line under
  the action-icon column whenever a neighboring cell's content height varied
  (e.g. the Type column briefly rendered as two stacked lines). Diagnosed
  (never fully proven) as `<ion-button>`'s internal shadow-DOM/default-sizing
  interacting badly with table cell `vertical-align`/border rendering — an
  attempted fix (constraining `ion-button`'s height/box-shadow via CSS) made
  it visibly *worse*, not better, and was immediately reverted. Rather than
  keep patching, the **whole feature was reverted to the git-committed
  baseline** (`git checkout HEAD -- master-data.page.{html,scss,ts}`) per
  explicit user instruction, keeping the backend `is_active` support intact,
  then **rebuilt from scratch** mirroring `users.page.html`'s already-working
  action-button pattern exactly: plain `<button class="action-btn action-btn--
  info/edit/delete">` elements instead of `<ion-button>`, same CSS class
  shape as Users Management's `.um-btn`/`.um-btn--*`. This second build had
  no border/alignment issues. **Lesson:** when a layout bug resists two
  targeted CSS fixes and a working reference implementation exists elsewhere
  in the same codebase, rebuild to match the reference structurally rather
  than keep patching the broken one.
- Deactivating a product only removes it from the **booking-picker**
  dropdown (backend-filtered, no frontend logic needed) — it remains fully
  visible and toggleable in Master Data, and existing bookings referencing it
  are entirely unaffected (see the backend debug log for why: `product_name`
  on a booking is a frozen snapshot copied in at creation time, never a live
  join back to the `products` table).

**User Management (`users.page.*`) soft-deactivation + role display:**
- Added a Status column (same toggle pattern as Master Data), disabled on the
  logged-in user's own row (`isSelf()`) to mirror the backend's
  self-deactivation guard.
- Removed the User ID column per user request (no longer surfaced in the
  main table; still shown in the per-row detail/view modal).
- Added a Role column (colored badge, e.g. green "Operator Admin", blue
  "Operator Staff") reading the existing `u.role.name` the API already
  returned — no backend change needed for this specific column.
- Fixed a column-width regression right after adding the Role column: `.col-
  email` had no `max-width`, so as a flexible table column it absorbed all
  spare width, visibly cramping the newly-added Role/Created At/Status
  columns to its right. Capped it at `max-width: 260px` with
  `word-break: break-word`.

**Add/Edit User modal — role picker for `operator_admin` (succession-
planning scenario):**
- Real motivating case from the user: if a company's sole `operator_admin`
  becomes unavailable and nobody else knows the login credentials, the

  today, `operator_admin` accounts can only ever create `operator_staff`

**Deposit-notice / receipt PDF text tweaks:** requested initially against the
**wrong template** — `receipt-activity.page.html` (the on-screen Angular
receipt page component) rather than the actual backend-generated,
downloadable PDF behind the "Resit Deposit/Deposit Receipt" button
(`rural-tourism-backend`'s `utils/bookingPdfGenerator.js`, a server-side

"the PDF you get when you click this button" and "the on-screen receipt
page that looks similar" can be two entirely separate templates in two
separate repos — confirm which one a screenshot actually came from (exact
title text, header layout, field labels) before editing, rather than
assuming the more familiar/nearby file is the right target.

## 4. Recalling a paid booking back to Pending unexpectedly navigated away from Booking Details

**Symptom:** using the "Recall" action on a paid booking's detail page
(`booking-detail.page.ts`) successfully reverted its status to Pending, but
immediately navigated the user back to `booking-home` (or `/home` if arrived
from the dashboard) instead of staying on the same booking's detail page.

**Root cause:** not a bug — `recallBooking()`'s success handler explicitly
called `this.goBack()` right after updating local state and showing the
success toast (mirroring `cancelBooking()`'s identical pattern a few lines
above it, which has the same "action complete, leave the page" behavior).
This was a deliberate UX choice, just one the user wanted changed for recall
specifically.

**Fix:** removed the `this.goBack()` call from `recallBooking()`'s success
branch only. The booking's local state was already being updated in-place
(`this.booking = { ...this.booking!, status: 'pending' }`) before the
navigation call, so removing it simply lets the page re-render with the new
status instead of leaving — the heading, status badge, and action buttons
(which all gate on `booking.status`) correctly flip to show Edit/Cancel
instead of Recall without any other change needed. `cancelBooking()`'s
identical `goBack()` call was left untouched, since only recall's behavior
was in scope.

## 5. Add Master Data modal expanded indefinitely on mobile, hiding the Save button behind many added products

**Symptom:** on mobile, adding several pending products in the "Add New
Master Data" modal before saving made the modal keep growing taller with
each addition, eventually pushing the Product Name input, Save/Cancel
buttons, and later rows out of the visible viewport with no reliable way to
scroll down to them.

**Root cause:** `.mini-table-wrap` (the pending-items list inside the modal)
had `overflow: hidden` and no height cap, so it grew unbounded with the
number of pending rows. `.master-modal` itself does have `max-height` +
`overflow: auto`, which should in principle make the whole modal scrollable,
but relying on the outer modal's scroll wasn't reliable enough on mobile
Ionic/WebKit to reach the button row once the pending list got long.

**Fix:** capped `.mini-table-wrap` at `max-height: 260px` with its own
internal `overflow-y: auto` (`overflow-x: hidden`), and made the mini-table's
header row `position: sticky; top: 0` so column labels stay visible while
scrolling through many pending items. This keeps the modal's overall height
fixed regardless of how many products are queued up — only the product list
itself scrolls internally, so the Save/Cancel buttons and the "Nama Produk"
input above the list stay reachable at a constant position on screen.
