## 1. Release APK: API calls fail after switching `androidScheme` to `https`

**Symptom:** the signed release APK showed a generic "Unable to connect to
server" on login. The backend was independently confirmed healthy (curl worked
fine), the correct API URL was confirmed compiled into the bundle, and
`adb logcat` showed **no** useful error at all — no network errors, no WebView
console output, nothing tagged `chromium`/`CapacitorHttp`/`Capacitor`.

**Root cause:** `capacitor.config.ts`'s `androidScheme` had been switched from
the default `capacitor` to `https` as part of Play Store production hardening
(dropping cleartext/mixed-content allowances now that the backend is served
over HTTPS). This changes the WebView's **origin** from `capacitor://localhost`
to `https://localhost`. The backend's CORS allowlist only listed
`capacitor://localhost` / `http://localhost`, so every request was blocked by a
CORS preflight failure before it ever left the WebView. See the backend debug
log `DEBUG_LOG_2026-08-10.md` §1 for the server-side fix.

**Why `adb logcat` showed nothing:** a blocked CORS preflight is handled
entirely inside the WebView's networking stack; Capacitor doesn't forward
WebView console/network errors to Android's system log by default. Logcat is
the wrong tool for this class of bug — it's only useful for native-level
crashes, permissions, and OS-level events.

**Debugging a signed release build with live DevTools (`chrome://inspect`):**

Release builds don't expose a remote-debugging socket by default — Capacitor
only enables it when `BuildConfig.DEBUG` is true, which a signed release build
never is. To inspect a *release* APK's WebView console and network tab
directly:

1. Enable Developer Options + USB debugging on the phone, connect via USB,
   accept the RSA fingerprint prompt (`adb devices` should list it as
   `device`, not `unauthorized`).
2. Temporarily force debugging on in `android/app/src/main/java/.../MainActivity.java`:
   ```java
   package com.sabah.ruraltourism;

   import android.os.Bundle;
   import android.webkit.WebView;
   import com.getcapacitor.BridgeActivity;

   public class MainActivity extends BridgeActivity {
       @Override
       public void onCreate(Bundle savedInstanceState) {
           super.onCreate(savedInstanceState);
           WebView.setWebContentsDebuggingEnabled(true);
       }
   }
   ```
3. Rebuild and install:
   ```sh
   npm run full-release
   cd android && ./gradlew assembleRelease
   adb install -r app/build/outputs/apk/release/app-release.apk
   ```
4. On the PC: Chrome → `chrome://inspect#devices` → open the app on the phone
   (must be foregrounded) → the WebView appears under the device with an
   **inspect** link. Opening it mirrors the phone screen live and gives full
   Console + Network tabs.
   - If the device shows up but no WebView entry appears underneath it, make
     sure the app is actually open/foregrounded on the phone, then refresh
     `chrome://inspect#devices`.
   - If it still doesn't appear, run `adb kill-server && adb start-server` —
     Chrome's USB port forwarding can get stuck after a device reconnects or
     the app relaunches mid-session — then refresh again.
5. Reproduce the bug in the mirrored window (input can be typed directly into
   the mirrored DevTools window, or on the phone itself — they're synced). The
   Console tab shows the exact browser-level error immediately, e.g.:
   ```
   Access to fetch at 'https://api.rutec.my/api/auth/login' from origin
   'https://localhost' has been blocked by CORS policy: Response to preflight
   request doesn't pass access control check: No 'Access-Control-Allow-Origin'
   header is present on the requested resource.
   ```
   This is far faster than guessing from native-side symptoms — the exact
   failing URL, origin, and reason are all present in one line.
6. **Revert step 2 before shipping.** A signed build intended for the Play
   Store shouldn't ship with debugging force-enabled. Rebuild clean
   (`npm run full-release` → `gradlew assembleRelease`/`bundleRelease`) and
   reinstall to confirm the app still works without it.

**Verifying the backend fix without rebuilding the app:** once the CORS
allowlist is updated server-side and redeployed, confirm with curl (see
backend debug log §1) before retesting on-device — this rules out the app as
the remaining variable if login still fails after redeploy.
